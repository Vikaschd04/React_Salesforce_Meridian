Meridian — a headless commerce storefront on Salesforce

A React storefront and a Node backend-for-frontend sitting in front of Salesforce as the system of record. Salesforce owns the catalog, customers, orders, promotions and cases; the BFF is the only thing that speaks to it; the browser only ever speaks to the BFF.

The three layers

Each layer only talks to its neighbour. That single rule is what makes the storefront headless: swap Salesforce for mock data, or swap the React front end for a mobile app, and nothing else has to change.

Placing an order — the critical path

The one flow that touches every layer. Numbered because it genuinely is a sequence: each step depends on the one before it, and money only moves once the price is proven.

Cart submitted

Browser posts only { id, qty } plus shipping, promo code and a payment token. No prices are sent.

Validate

Zod parses the payload strictly; unknown fields are rejected outright.

Price from source

Live Product2 + PricebookEntry lookup gives the trusted unit price and stock for every line.

Promotion

Coupon re-validated against Coupon / Promotion rules — minimums, expiry, usage limits.

Totals

Server computes subtotal − discount + shipping + tax. This figure, not the client's, is what gets charged.

Take payment

Stripe PaymentIntent created and confirmed. A decline stops here with a 402 and no order is written.

Write the order

Order + OrderItems in one Composite call, then activated via standard Status.

Order management

Delivery group, shipping line and per-line tax added, then createOrderSummary rolls up the OMS record.

Settle inventory

Stock decremented, coupon redemption recorded, confirmation returned to the shopper.

Why this order matters: price is established from Salesforce before the card is charged, and the card is charged before the order is written — so a shopper is never charged for an order that failed to save, and never charged a price they supplied themselves.

The other flows

Each one follows the same layer discipline: browser → route → store → Salesforce.

Product listing & search

  • Shop page reads filters + page from the URL
  • GET /api/catalog?page&q&roast&origin&price&sort
  • Cached SOQL returns the full active catalog
  • Filter → sort → facet across all products
  • Slice one page (10) + facets back to the browser

Guided selling

  • Shopper answers 4 questions
  • POST /api/guided/recommend
  • Score every Product2 on roast, flavour, body, brew
  • Rank → top 3 with match % and reasons
  • If logged in, taste profile saved to their Contact

Bundles

  • Bundle is itself a Product2 (bundle-* code)
  • Components read from the junction object
  • Live component prices → saving calculated
  • Added to cart as one ordinary line
  • Checkout, stock and OMS need no special case

Live order tracking

  • Merchant changes Order.Status in Salesforce
  • Change Data Capture emits OrderChangeEvent
  • BFF subscribes, maps it to an app event
  • Server-Sent Events push to the open page
  • Status and timeline update with no reload

Accounts & auth

  • Signup creates a Person Account + Contact
  • bcrypt hash stored server-side only
  • Signed httpOnly cookie carries the session
  • Orders link to the shopper via Order.AccountId
  • Guests check out with an email instead

Support

  • Contact form posts to /api/support
  • A real Salesforce Case is created
  • Agent replies as a public CaseComment
  • Shopper sees the thread under Account → Support
  • Guests get a case number to quote

Extending to B2B

The build today is B2C — individual shoppers as Person Accounts. The architecture is commerce-model agnostic, so B2B is additive: the layers, the order pipeline and the payment abstraction all stay exactly as they are. Everything below is a documented extension point, not yet implemented.

Roadmap · not built

Company accounts & buyers

Business Account + Contact roles and BuyerGroup — buyers belong to a company, with admin vs purchaser permissions.

Contract & tiered pricing

Multiple Pricebook2 records resolved per account, plus quantity-break schedules. The catalog already reads a pricebook — it just resolves a different one.

Quotes / RFQ

Quote + QuoteLineItem: buyer requests, a rep prices it, and the accepted quote converts into the same Order pipeline.

Approvals & spend limits

Salesforce Approval Processes or Flow gate orders above a threshold before they activate.

PO numbers & Net-30

Purchase-order field plus a "pay by invoice" provider — the payment layer is already an abstraction, so this is a third provider alongside mock and Stripe.

Reorder & requisition lists

Quick-order pads by SKU/CSV and named saved lists — built on the order history and wishlist patterns already in place.

Runtime configuration

Two switches decide what the same codebase talks to — which is what makes the demo reliable and the integration real.

SettingOptionsEffect
DATA_SOURCE mock salesforce Chooses the implementation behind every store/ function. Routes, UI and tests are identical either way.
PAYMENT_PROVIDER mock stripe Offline fake charges, or real Stripe test-mode PaymentIntents with Elements, webhooks and refunds.
npm run sf:setup — Idempotently provisions custom fields, objects, picklist values, CDC and the integration permission set.
